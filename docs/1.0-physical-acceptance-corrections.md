## Scroll Defect and Evidence

The previous limit synthesized the scramble origin from container top + controls
height. The fixed outer positioned-area frame was not itself a clipping boundary;
only the inner, implicitly animated ScrollView was clipped. A frame constrains layout,
not drawing, so positioned/transitional content was not independently contained at
an actual measured exclusion band. Longer content exposes this missing guarantee;
there is no 7x7-specific defect in notation or font metrics.

`TimerScrambleScrollViewport` now measures the real area origin, limits the inner
viewport and clips the entire positioned band outside its animated child. Native
ImageRenderer tests with 720- and 8,000-point overflowing content both render only
rows 110...232, before Timer top 245 (12-point gap). Geometry tests cover placement,
origin differences, arbitrary content heights, zero room and nonfinite inputs.
This verifies the structural correction, not a reproduction of the user's device's
exact safe-area/transition timing. Physical 7x7 acceptance remains required; 6x6's
accepted font/layout and Auto-shrink algorithm were not redesigned.

## FTO Findings and Optimization

Before editing, a 30-state native macOS JavaScriptCore profile measured cold solver
2,654 ms; warm median 928 ms, mean 1,532 ms, maximum 7,973 ms. Facelet conversion
was approximately 0.2-0.4 ms. These are diagnostic CLI runtime measurements, not
physical iOS timings or a directly comparable app throughput benchmark.

Source inspection found:

- The VM/tables were already cached; no per-request table rebuilding needed fixing.
- Serial refill was legitimate for one VM but limited independent generation to one
  producer. Empty foreground consumption queued a fresh solve behind an in-flight
  refill instead of consuming that completed refill: avoidable double work/wait.
- Facelet interpretation shared the solver queue and could wait behind heavy search.
- UI context-safe prefetch/activation and renderer state interpretation already exist;
  they are not replaced. The renderer does not invoke the random-state solver.

Keep the four-entry consume-once reserve; do not increase its depth. Two independent
solver VMs now run on separate user-initiated serial queues. No JS objects cross
queues, tables initialize once per worker, and the immutable source string is read
once. The storage-plus-in-flight reservation is bounded to four; at most two solves
are active. Consumers join pending producer work rather than scheduling another
foreground solve. Refill starts immediately on consumption/completion and stops at
capacity. Failure does not create an endless retry loop; a later explicit request
can retry. A separate lightweight VM interprets facelets without solver contention.
There are no persistent timers or unbounded refill tasks; ordinary request/context
invalidation remains unchanged. Cached VMs intentionally remain process-lifetime.

The random-state solver, RNG contract, notation, fixture data and renderer's state
engine are unchanged. Independent full-state oracle coverage remains 98 comparisons.

Fresh independent pool in the actual app test runtime, same production generator;

between consumption attempts. Engine delivery only, not touch-to-render/device FPS.

| Warm reserve maximum | 0.017 ms |

| Sustained median | 0.028 ms |
| Sustained maximum | 337.448 ms |
| Sustained delivered throughput, including pauses | 8.530 / second |

Earlier app samples in this pass: cold 431-634 ms; sustained maxima 11.7-166 ms.
Variability remains real. An unoptimized macOS CLI stress run of the same producer

(two solvers plus state VM/process). This is not the app's or an iPhone's memory
measurement. Two VMs trade bounded additional table memory/CPU for throughput;
no claim of zero latency or universally immediate reserve exhaustion is warranted.
