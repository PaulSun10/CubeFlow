# WCA Recovery and Local Battle - 2026-11-16

## WCA incident and fix

- Confirmed from source and mocks: an ambiguous refresh can spend both sends for the persisted UUID and leave `recoveryPending` on disk. The v0.16.0 app then continued showing Recovery Pending, although the owner would not send a third request. Settings' profile refresh did not proactively recover a pending refresh if the WCA access token still looked valid. My Competitions did not reload after same-session recovery.
- The pending state covers an interrupted durable dispatch, nonterminal dispatch failures (including throttling, transport failure and ambiguous HTTP responses), and rejected refresh data such as an older generation or an expired access token. A wrong-session response now records the same safe pending state rather than leaving the operation marked in flight. Structured Broker 401/502 failures and conflicting equal-generation credentials are separate, confirmed uncertainty paths.
- Suspected triggers remain separate from this failure mechanism. Broker-session expiry, WCA access expiry/401, transport errors, throttling, ambiguous server/response errors, rejected replays and structured broker failures take different paths. There is no sanitized trace of the original iPhone event. Git history places the bounded pending-state behavior in the Broker coordinator introduction; retiring the old provider did not introduce that policy. This does not rule out a later trigger.
- Manual Refresh now attempts an eligible recovery before loading the profile. Reconnect, foreground activation and a one-shot Retry-After deadline reuse the same coalesced operation. A URLSession offline error no longer immediately spends the second send; transport errors that could have reached the server retain the existing bounded same-key policy. The deadline and send budget persist across restart.
- After budget exhaustion, confirmed uncertainty, or Broker-session expiry, the account UI offers WCA sign-in rather than an ineffective Refresh. No automatic sign-out or sign-in, extra refresh budget, ticket replay, token migration, or broad retry loop. A still-valid WCA token keeps its existing narrowly scoped API behavior; the app does not assume a recoverable refresh token. Cached profiles and Keychain state remain session-isolated. Session revision, ordered persistence, token generation checks, and the one retry after WCA 401 remain in place.
- My Competitions retries explicitly through recovery and reloads after same-session recovery when it had a settled failure. Public My Results still uses the existing public result path.
- No Web change is needed to fix the proven app issue. Transparent recovery after exhausted ambiguous sends would need an authoritative Broker contract for operation status/recovery. Do not grant an extra client send or generate a new UUID as a workaround.

## Battle behavior

- Local Head-to-Head and Side-by-Side own a shared event and one round assignment, identified by a request UUID. Both players use that assignment; active and completed solves keep it for scoring. A single reserved next assignment becomes visible first to the finisher, then to both at the completion barrier. Event changes apply to both and are locked during round activity. Nearby's host-owned flow is separate and unchanged.
- Touch retains its joint readiness with a touch opponent. Smart Timer retains hardware run correlation. Both go through the same start barrier. Manual can type the next time early; a blocked submission changes no score, preserves the text, and is not queued. The waiting text is localized in all 19 supported languages.
- v0.16.1 presentation: waiting feedback is shown only when a Smart Cube is verified ready for the next scramble while blocked, or when a manual Save/Return submission was rejected by that round's barrier. No passive manual, touch or Smart Timer waiting message. The shared footer and draft handling remain in place.
- Smart Cube tracks each assigned peripheral's canonical stream while waiting. It can verify the next target, revoke readiness on deviation, and restore it when the target matches again. The existing 3x3 guidance controller validates identity, source facelets, target, generation, device and canonical sequence before adoption. The 2x2 path retains state-based progress rather than adding a new solver. The previous round cannot be started/finished again; stale callbacks cannot consume a later assignment.
- Existing local Battle is open-ended and keeps results in the active match, not the Solo solve database. Exit invalidates queued generation by identity; a native generation that already started may finish in the background but cannot publish or prefetch more afterward. If generation has not finished when the first solve ends, that player sees the existing loading placeholder, not the previous scramble presented as the next one.
